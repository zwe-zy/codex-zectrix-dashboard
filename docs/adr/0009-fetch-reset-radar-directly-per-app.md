# Fetch reset radar directly in each App

Each App that needs reset-radar data will request the public upstream API through its own adapter instead of depending on a shared Cloudflare Worker. The Companion reads once immediately at startup and then once per hour, coalescing missed sleep intervals into one observation; at this frequency, direct requests add negligible CPU, memory, and network cost while avoiding KV, authentication, deployment, additional failure points, and cross-App contract ownership. A cloud service should be introduced only if a future requirement needs centralized history, policy, or data unavailable from independent upstream reads, not merely because another App consumes the same public API.

The Companion validates only recognized reset and Watch evidence needed by its radar display, allowing unrelated statistics, provider text, source details, and unknown additive fields to evolve without disabling valid evidence. Unknown reset types or invalid Watch fields disable only that evidence and can never be reinterpreted as no active watch; only the semantic fields needed by the display are persisted, while response-generation timestamps, transport metadata, and complete raw JSON are not retained.

Production uses the fixed HTTPS status endpoint at `codex-resets.com`; changing providers is a reviewed adapter change rather than runtime configuration. Only tests may override the endpoint to use a controlled local server.

The hourly conditional request runs in the existing Companion deadline loop rather than a dedicated thread or async runtime. A three-second connection timeout and five-second total timeout bound the optional source's effect to an accepted occasional task-observation delay, while avoiding another thread stack, synchronization layer, and resident worker.

The Companion reads at most 64 KiB from a status response even when no content length is declared. An oversized response is rejected without being logged or persisted, and previously validated evidence follows the normal freshness and expiry rules.

Diagnostics expose only `radar_source=current|stale|unavailable`, `radar_reason=none|network|rate_limited|upstream_unavailable|invalid_response|response_too_large`, and, when relevant, the next allowed request time. `stale` means previously validated evidence is still eligible for display although the latest request failed; `unavailable` means no reliable display evidence remains. Diagnostics never include the upstream response body or text, source URL, ETag, request headers, or forecast window.

ETags and freshness-only confirmations are kept in memory and are not persisted. A restart always performs an immediate unconditional request. If that request fails, a persisted Watch may remain visible until its intrinsic expiry and a persisted reset confirmation may remain visible through its 24-hour announcement window, both marked stale; a persisted no-Watch result is not treated as current after restart and therefore becomes unavailable. This keeps hourly successful checks from causing heartbeat writes while conservatively handling an offline restart.

Verification uses three existing public seams: a real Companion process against a controlled local upstream for scheduling, HTTP behavior, size limits, and cache recovery; domain and renderer tests for evidence precedence, expiry, and the 400-by-300 display; and the diagnostics CLI for status reporting and redaction. The reset radar does not introduce Cloudflare tests, a dedicated worker-thread harness, or a second runtime architecture.
