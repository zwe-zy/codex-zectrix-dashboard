# ZECTRIX NOTE4 Codex 状态牌设计

日期：2026-08-31

## 1. 目标

在 Windows 上运行一个轻量后台 companion，从本机 Codex 读取账户额度和最近任务状态，生成 400×300 黑白状态牌，并通过 ZECTRIX 官方云端 API 推送到 NOTE4。

最终设备在正常使用时只需要供电和 Wi-Fi，不需要通过 USB 与电脑保持数据连接。设备保留原厂固件，不刷写 ESP32-S3。

## 2. 已确认需求

- 设备：ZECTRIX NOTE4 V1.0，ESP32-S3-WROOM-1 N16R8，4.2 英寸 400×300 黑白墨水屏。
- 平台：Windows 与 Codex Desktop。
- 传输：保留原厂固件，通过 ZECTRIX Cloud 开放 API 推送图片。
- 屏幕字段：
  - 最近任务是否仍在运行或已经完成；
  - 剩余额度百分比；
  - 对应额度窗口的重置时间；
  - 最近一次成功上传画面的时间。
- 隐私：不显示或上传任务标题。
- 刷新目标：每 60 秒观察一次任务状态；仅在可见状态变化时上传新画面。
- 视觉：采用已确认的 P「怪盗剪贴风」，但不使用任何原作角色、Logo、专属符号或原始素材。

## 3. 非目标

- 不控制、暂停、结束或重新运行 Codex 任务。
- 不显示提示词、回复、推理、工具参数、计划文本、项目路径或账户身份。
- 不显示任务标题，即使本地 Codex 可以提供标题。
- 不加入第三方“重置雷达”或非官方预测。
- 不修改 NOTE4 固件，不直接驱动 SSD2683，不要求长期 USB 数据连接。
- 第一版不提供复杂桌面 GUI；安装、预览和诊断采用少量明确命令完成。

## 4. 推荐实现路线

以 MIT 许可的 [`BarryBarrywu/codex-zectrix-dashboard`](https://github.com/BarryBarrywu/codex-zectrix-dashboard) 为基础移植到 Windows，而不是重新实现全部协议与推送逻辑。

保留：

- Rust companion 主体；
- 持久 `codex app-server` 会话；
- Codex 配额与任务状态归一化；
- 400×300 图片渲染；
- ZECTRIX 设备发现、页面选择和 changed-frame 上传；
- fixture、fake server 和渲染测试结构。

替换或扩展：

- macOS Keychain → Windows Credential Manager；
- launchd → 当前用户的 Windows 任务计划程序；
- macOS 路径与进程发现 → Windows Codex 安装发现；
- 原看板主题 → 已确认的 P 风格主题；
- 默认显示标题 → 强制无标题单任务状态视图。

不选择另外两条路线：从零编写 Python/Node companion 会重复已有协议和测试工作；刷自定义固件会扩大风险，且与“保留原厂固件”的决定冲突。

## 5. 系统结构

### 5.1 `CodexSource`

负责启动并维持一个本地 `codex app-server` 会话，完成协议握手和能力检查。

启动时必须验证当前 Codex 是否提供以下能力：

- `account/rateLimits/read`；
- `thread/list` 和 `thread/read`；
- `Thread.status` 和最近一轮 `Turn.status`。

若能力缺失，程序应明确报告 Codex 版本不兼容，而不是猜测或抓取桌面 UI。

### 5.2 `StatusNormalizer`

把 Codex 协议中的多种状态转换为固定、可测试的屏幕模型。它只接收必要字段，不保存完整任务内容。

### 5.3 `DashboardRenderer`

把屏幕模型渲染为固定 400×300 的 1 位黑白 PNG。渲染器不联网，也不读取密钥。

### 5.4 `ZectrixClient`

负责：

- 验证 ZECTRIX API Key；
- 列出兼容设备和可用页面；
- 将 PNG 上传到用户选定页面；
- 返回可区分的认证、网络、设备和服务端错误。

### 5.5 `Scheduler`

协调观察、渲染、图片哈希、上传节流、重试和本地状态缓存。各组件之间通过归一化数据结构通信，避免把网络、协议和渲染逻辑写在一个文件中。

### 5.6 `Setup`

负责首次配置、预览、明确的首次上传确认和开机自启安装。它不负责常驻观察。

## 6. 数据来源和选择规则

### 6.1 额度

额度来自本机 `codex app-server` 的 `account/rateLimits/read`，不是 OpenAI API 组织用量接口，也不抓取 Codex 界面。

选择顺序：

1. 优先使用 `rateLimitsByLimitId["codex"]`；
2. 若该结构不存在，回退到兼容字段 `rateLimits`；
3. 优先使用选中额度桶的 `primary` 窗口，缺失时使用 `secondary`；
4. `剩余额度 = clamp(100 - usedPercent, 0, 100)`；
5. 重置时间必须来自同一个窗口的 `resetsAt`，并转换为 Windows 当前时区；
6. 若窗口不存在，不用零值伪装有效数据，显示 `--%` 和 `--:--`。

额度在启动时立即读取，之后每 10 分钟读取一次。若 app-server 主动发出额度更新通知，可提前刷新本地状态。

### 6.2 最近任务

只观察最近更新的顶层任务：`parentThreadId` 为空，并按 `updatedAt` 或 `recencyAt` 选择最新项。子代理任务不单独占据状态牌。

状态映射：

| Codex 状态 | 屏幕状态 |
| --- | --- |
| `ThreadStatus.active` 或最近 `TurnStatus.inProgress` | 任务运行中 |
| 最近 `TurnStatus.completed` | 已完成 |
| 最近 `TurnStatus.failed` 或 `ThreadStatus.systemError` | 失败 |
| 最近 `TurnStatus.interrupted` | 已中断 |
| 没有任何可观察任务 | 暂无任务 |
| 无法取得可信状态 | 状态暂不可用 |

任务每 60 秒观察一次。若 app-server 提供相应通知，可以立即更新，但轮询仍作为恢复和一致性保障。

## 7. 屏幕模型

渲染器只接收下面的最小模型：

```text
DashboardState
  task_state: running | completed | failed | interrupted | empty | unavailable
  quota_remaining_percent: 0..100 | unavailable
  quota_resets_at: local datetime | unavailable
  quota_stale: boolean
  uploaded_at: local datetime | absent
```

模型中不允许出现任务标题、任务 ID、提示词、项目路径或用户身份字段。

## 8. P 风格视觉规范

- 画布固定为 400×300，输出 1 位黑白 PNG。
- 左上保留小型 `CODEX // NOW` 识别文字。
- 上半部使用不规则黑色斜切块承载任务状态，状态是第一视觉层级。
- 左下使用大号斜置数字显示剩余额度。
- 右侧使用倾斜白底黑框信息块显示重置时间。
- 右下显示 `UPDATED HH:MM`，含义是最近一次成功上传变化画面的时间，不是无条件每分钟递增的时钟。
- 网点必须足够粗，避免在 400×300 屏幕上变成噪声；关键文字区域保持纯色底。
- 中文字体使用可再分发的开源字体子集，覆盖固定状态词和数字。不得依赖联网字体。
- 不复制 Persona 5 或其他作品的 Logo、角色、剪影、专属图形或原始 UI 资产；只使用通用的斜切、网点和剪贴视觉语言。

## 9. 更新与上传语义

1. Scheduler 取得新的额度或任务状态。
2. StatusNormalizer 生成 `DashboardState`。
3. 与上次成功状态比较；若可见字段不变，不渲染、不上传。
4. 若可见字段变化，使用当前时间作为候选 `uploaded_at` 渲染 PNG。
5. 对 PNG 计算哈希；若与上次成功图片相同，跳过上传。
6. 上传成功后，才把候选时间和图片哈希写入本地缓存。
7. NOTE4 根据原厂固件配置检查云端页面；目标检查间隔为 1 分钟，若固件只提供离散选项则使用最接近的可用间隔。

这保证“更新时间”只代表真实上传，不会因为时钟变化强迫系统每分钟上传一张内容相同的图片。

## 10. 隐私与密钥

- ZECTRIX API Key 保存到 Windows Credential Manager。
- 普通配置文件只保存设备 ID、页面 ID、轮询间隔和显示选项。
- 本地缓存只保存最小屏幕模型、上次成功哈希和成功上传时间。
- 日志不得包含 API Key、完整 Codex 响应、任务标题、任务 ID、账户信息、设备原始响应或图片二进制。
- 上传边界仅为最终 400×300 PNG；由于画面无标题，云端不会收到任务标题。
- 首次上传必须在本地预览后获得用户明确确认。

## 11. Windows 安装与运行

发行物包含一个签名或可校验哈希的 Windows 可执行文件，支持：

- `setup`：配置密钥、选择设备与页面、生成预览、确认首次上传、安装自启；
- `run`：前台运行，便于调试；
- `preview`：只生成本地 PNG，不联网；
- `status`：报告 companion、Codex 连接和最近上传状态，不显示敏感数据；
- `uninstall`：移除自启并删除非敏感配置；密钥删除作为单独的明确选择。

自启使用当前用户的 Windows 任务计划程序，在登录时启动隐藏窗口进程，不要求管理员权限。配置和缓存位于当前用户的本地应用数据目录。

## 12. 错误处理

- Codex 暂时不可用：保留最后有效任务状态；连续 3 分钟无法确认后显示“状态暂不可用”。
- 额度暂时不可用：保留最后有效额度；超过 30 分钟后在画面加小型“数据过期”标记。
- 首次启动即无数据：显示占位值，不显示 `0%` 或虚构重置时间。
- ZECTRIX 网络错误：按 1、2、5、15 分钟退避重试，最多保持 15 分钟间隔；新状态覆盖尚未上传的旧状态。
- ZECTRIX 认证错误：停止自动上传并在本地诊断中提示重新运行 `setup`，不清空设备当前画面。
- 设备或页面失效：停止自动上传，要求重新选择，避免把图片发送到意外目标。
- Codex 协议不兼容：报告缺失能力和检测到的 CLI 版本，不改用屏幕抓取。

## 13. 测试策略

### 13.1 单元测试

- 所有额度选择和百分比计算分支；
- 所有任务状态映射；
- 顶层任务选择和子代理排除；
- 新鲜、过期、首次无数据状态；
- changed-state、changed-frame 和上传节流；
- 日志脱敏。

### 13.2 渲染快照

为运行中、已完成、失败、已中断、暂无任务、数据过期和无额度各维护一张 400×300 基准图。测试尺寸、像素模式、文字边界和关键区域对比度。

### 13.3 集成测试

- fake Codex app-server：协议握手、额度读取、任务通知、断线重连和不兼容协议；
- fake ZECTRIX：设备发现、首次上传、认证失败、重试和重复图片抑制；
- Windows Credential Manager：写入、读取和删除测试，不在输出中显示密钥；
- Windows 任务计划程序：安装、重复安装、启动和卸载。

### 13.4 实机验收

- NOTE4 在不通过 USB 连接电脑传输数据时正常更新；
- Codex 任务从运行到完成后，状态牌在目标观察周期内更新；
- 额度和重置时间与 Codex 当前账户状态一致；
- P 风格画面在实体屏幕上无明显文字裁切，网点不过密；
- 相同状态不会重复上传；
- Windows 注销或重启后 companion 自动恢复；
- 配置、缓存和日志中找不到 API Key 或任务标题。

## 14. 验收标准

满足以下条件即完成第一版：

1. 在当前 Windows 机器上可以读取 Codex 额度和最近顶层任务状态。
2. 生成的图片严格为 400×300 黑白 P 风格，且不含任务标题。
3. 首次上传前有本地预览和明确确认。
4. NOTE4 通过 Wi-Fi/云端取得更新，USB 仅用于供电。
5. 任务状态观察间隔为 60 秒，额度按 10 分钟或通知更新。
6. 只在可见状态变化时上传，并正确记录最近成功上传时间。
7. 网络、认证、无数据和协议不兼容均有明确且安全的行为。
8. Windows 开机登录后自动运行，无需管理员权限。
9. 自动化测试通过，并完成一次当前 NOTE4 的实体设备验收。

## 15. 已知风险

- `codex app-server` 属于正在演进的本地协议。实现必须通过能力检查与适配层隔离变化，不能把协议字段散落到各模块。
- ZECTRIX 云端 API、设备页面 ID 和固件可用刷新间隔需要在首次安装时实测确认。
- 实体墨水屏的点阵、字体栅格和残影只能通过当前设备最终验收，浏览器预览不能替代实机测试。
- 当前工作目录不是 Git 仓库，因此本规范可以保存但不能在此目录提交；实现开始时应在独立源码仓库中建立可追踪历史。
